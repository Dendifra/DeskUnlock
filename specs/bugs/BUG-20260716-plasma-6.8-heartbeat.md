# BUG-20260716: Plasma 6.8 lock-screen migration incompatibility

## Summary
The Plasma lock-sync installer must recognize the Plasma 6.8 heartbeat and preserve older QML state backups during migration.

## Reproduction
- Method: regression fixture.
- Test: `desktop/tests/test_plasma_lock_sync.sh`.
- Evidence before fix: `expected exactly one graceLockTimer anchor, found 0`.

## Expected Behavior
The installer accepts the supported Plasma 6.8 heartbeat layout, keeps authentication user-initiated, preserves password entry and proximity behavior, and remains compatible with the supported legacy timer layout.

## Actual Behavior
The installer originally rejected the Plasma 6.8 heartbeat. After that compatibility fix, migration still reused the fixed state paths `MainBlock.qml.vendor` and `LockScreenUi.qml.vendor`: installation replaced the Plasma 6.7 snapshots with Plasma 6.8 QML, and rollback trusted the fixed names without checking which generation they contained.

## Root Cause Analysis
`find_named_timer` recognized only the legacy timer ID and `patch_interaction_qml` required the legacy timer's `root.clearPassword()` body. Separately, `plan_qml`, `install`, and `remove` treated fixed state-backup names as current regardless of their bytes. The supplied state hashes match the legacy backups, while the installed Plasma 6.8 QML hashes differ; therefore the existing install path overwrote both historical snapshots.

## Fix
Recognize exactly one legacy authentication timer or Plasma 6.8 heartbeat timer. Remove the heartbeat's automatic trigger binding while retaining the legacy password-clear/restart behavior. Preserve Plasma's failure-restart call, reset the interaction guard after failure and when the UI hides, and keep new authentication requests tied to explicit mouse movement/click and Enter interactions. Store vendor snapshots under content-hash-qualified filenames, validate every existing snapshot before planning writes, select rollback data by verifying that patching it reproduces the managed QML, and retain snapshots after rollback. Unknown or mismatched backups fail before writes. The migration regression test seeds the actual old backup hashes and checks idempotence, byte-identical rollback, preservation, and fail-closed behavior.
