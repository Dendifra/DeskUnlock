# BUG-20260921-211500: Lock-screen authentication generation race

## Summary
DeskUnlock could issue a later PAM challenge through a delayed `passwd.active` edge after an earlier local/proximity challenge had already completed with a bad signature.

## Evidence
The pre-fix DMS bridge injected three independent starts: `phoneReturned()`, `passwd.onActiveChanged()`, and `localInteractionConsumed` reset on `passwd.active=false`. The same locked session therefore had no durable terminal generation state. The daemon already rejected concurrent same-peer requests with its semaphore, while the Android approval activity reused the current single-top activity intent; a second close-together challenge could therefore sign the wrong retained challenge and produce `bad-signature`.

## Root Cause
The lock-screen integration treated PAM activity as the local interaction edge and reset its duplicate guard when PAM became inactive. It had no single lifecycle state spanning local, PAM, and proximity triggers. Discovery rotation was not the cause: `run_challenge` copies the peer bond key into `PeerState` before waiting, while rotation only republishes session UUIDs.

## Fix
The DMS bridge now exposes the earliest existing lock-local wake edge from `Lock.qml`, routes all starts through one `AUTH_READY` / `AUTH_IN_FLIGHT` / `AUTH_CONSUMED` generation gate, ignores duplicate and stale completions, and permits a new generation only on a later explicit interaction. Lock teardown invalidates the generation and cancels the PAM context.

## Traceability
- Regression contract: `tests/auth_lifecycle.sh`
- Implementation: `desktop/dms/build-dms-syauth.sh`
