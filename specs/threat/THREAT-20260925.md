Produced by `/threat` on 2026-09-25, for `v0.1.0-beta.2`.

*observed* are different things, and this project has already shipped two defects

## 2. Assets and actors

| Asset | Why it matters |
|---|---|
| Bond key (per peer) | Forging it forges every unlock |
| Phone Ed25519 signing key | Held in Android Keystore, biometrically gated; the phone *is* the key |
| Pairing OOB code | Predicting it bonds a rogue phone |
| The authenticated session | The point of the whole system |
| Presence stream (RSSI, heartbeat) | Reveals when the operator is at the desk |

| Actor | Bounded capability |
|---|---|
| Remote network attacker | No path: nothing in the unlock loop listens on IP |
| Local radio attacker | BLE radio within ~10 m, can sniff and inject |
| Relay attacker | Two radios, low-latency link, one near each end |
| Co-located local user | Shell as another user on the same desktop |
| Root attacker | Already root (post-compromise; see the accepted risk) |
| Phone thief | Has the phone, not the desktop |
| Desktop thief | Has the desktop, not the phone |

**Trust boundaries:** the BLE air gap; `pam_syauth.so` running inside `login`
versus the user's daemon; `/var/lib/syauth` (root-owned) versus the user's
runtime dir; the Rust↔C boundary inside the PAM module (see `/ffi`).

## 4. The ten canonical abuse paths

| # | Path | Verdict | Evidence |
|---|---|---|---|
| 4.1 | **Relay** (two radios, low latency) | **PARTIAL — the timing budget is not measured** | D2 mandates a phone gesture per unlock, which defeats the passive class. The SPEC also claims a sub-100 ms RTT budget; **no RTT distribution exists in the repo**. Until it does, the *active* relay class is unproven. Finding T-101. |
| 4.2 | **Replay** | **MITIGATED, verified at three levels** | The running path is `orchestrator.rs` → `NonceCache` (64-entry `VecDeque`, LRU eviction on insert), checked *after* `verify_frame`. Covered by `syauth-presenced/tests/replay.rs::repeated_nonce_returns_replay`, `pam_e2e.rs::tc03_replay_returns_pam_auth_err`, and by the core's eight unit tests. See T-127 for what the reading turned up instead. |
| 4.3 | **MitM during pairing** | **MITIGATED, observed** | D5: LESC numeric comparison **plus** an app-level OOB code. Observed on hardware: the desktop rejects and closes the transaction when the two sides disagree (§6 pair engine log, 2026-09-24). |
| 4.4 | **Rogue device bonding** | **MITIGATED, observed** | SPEC T-004. Verified this session: an inbound bond request on an un-armed computer is answered with `Reject` and the session closes — `pair_engine.rs` refuses via `broker.request_oob_confirmation`, "no GUI means a closed failure". Reproduced 2026-09-24 18:57. |
| 4.5 | **PAM stack misconfiguration** | **DEVIATED — see docs/known-gaps.md** | D7 asks for `auth required` with a documented fallback. What is installed on the reference machine is `auth sufficient` for the greeter (DEV-006), approved by the operator. `sufficient` preserves the password fallback in *this* stack, but it is a weaker default than the SPEC describes and it is not what a reader of the SPEC would find. **This is the finding with the largest real-world surface in this document.** |
| 4.6 | **Phone-thief escalation** | **MITIGATED, design + Keystore** | D6: `setUserAuthenticationRequired(true)` on the signing key, so the biometric gate is enforced by hardware, not by app code. Not independently verified (would need the phone in hand and the app instrumented). Finding T-119. |
| 4.7 | **Desktop root ↔ key extraction** | **ACCEPTED RESIDUAL** | Documented in SPEC T-007. Root reads the keyring; root could do anything anyway. §7. |
| 4.8 | **Denial of unlock** | **MITIGATED, observed** | The password fallback exists and is the default; the greeter PAM line is `sufficient`, so a failed or absent phone falls through. Observed working this session. |
| 4.9 | **Presence inference / tracking** | **MITIGATED, observed** | D8: the **desktop** advertises a per-minute rotating session UUID; the phone scans. Observed: `pairModeUuidsFor` returns previous/current/future slots and the filter set rotates. The phone never advertises a stable identifier. |
| 4.10 | **Side-channel on bond-key comparison** | **MITIGATED, verified by grep** | `crates/syauth-core/src/mac.rs` routes every comparison through `subtle::ConstantTimeEq::ct_eq` (`computed.ct_eq(tag).into()`), declares the dependency in `syauth-core/Cargo.toml`, and carries `verify_is_constant_time_smoke`. Signatures verify through `verify_strict`, which rejects malleable ones. Resolved during this review: the claim was unverified, not false. |

## 5. Findings

Severity per the skill rubric. `Status: open` means a failing test is required
(§6); `accepted` means §7.

```
ID: T-101
Title: The relay timing budget is asserted but never measured
Severity: high
Attacker: Relay attacker (two radios)
Asset at risk: The authenticated session
Path: an attacker who relays the BLE link in real time defeats every
      cryptographic check, because the checks are about *who*, not *where*.
      The SPEC claims a sub-100 ms RTT budget makes the relay visible; nothing
      in the repository measures RTT under either condition.
Likelihood: medium (needs equipment and proximity to both ends)
Impact: critical (unauthenticated unlock)
Mitigation: measure and record the RTT distribution, normal versus relayed, as
      the skill requires; then set the budget from the measurement rather than
      from an assumption.
Status: open  ·  doc-only until the measurement exists (needs a second radio)
Owner: —
```

```
ID: T-102
Title: The replay matrix is claimed but has no test
Severity: high  →  WITHDRAWN, the premise was false
Attacker: Local radio attacker
Asset at risk: The authenticated session
Path: a recorded successful frame replayed inside the TTL window.
Mitigation: exists already, and I was wrong to say otherwise. The orchestrator's
      NonceCache is checked after verify_frame and before the success audit, and
      three tests cover it across two crates. I searched syauth-core for the
      replay defence, found a well-tested ReplayCache that nothing calls, and
      concluded the defence was missing — while the daemon was carrying its own.
Status: withdrawn (2026-09-25). Superseded by T-127.
```

```
ID: T-127
Title: Two replay caches, and the SPEC documents the one that never runs
Severity: low
Attacker: none directly — this is a truth defect, not an exploit
Asset at risk: the credibility of every other "mitigated" in this document
Path: SPEC §6 T-002 says "16-byte nonce + 64-entry LRU cache, 10 s TTL".
      syauth-core implements exactly that (`ReplayCache`, `DEFAULT_REPLAY_TTL =
      10s`, `DEFAULT_REPLAY_CAP = 64`), with eight unit tests, and re-exports it
      from the crate root. Nothing calls it: the running defence is
      syauth-presenced's own `NonceCache`, which has the 64-entry LRU cap and no
      TTL at all.
Mitigation: pick one. Either wire the core cache into the daemon and delete the
      local one, or delete the core one and correct the SPEC to describe what
      runs. The second is smaller and the TTL is not missed in practice: nonces
      are minted fresh per challenge, so an entry that never expires cannot
      falsely reject a legitimate response — the cap alone is enough.
      Until one of those happens, the SPEC describes a mechanism that is not the
      operative one, which is how a reader ends up reasoning about a 10-second
      window that does not exist.
Status: open  ·  doc-only until the choice is made
```

```
ID: T-105
Title: Constant-time comparison of the bond key is not demonstrated
Severity: high (if the claim is false)  →  withdrawn, the claim holds
Attacker: Co-located local user
Asset at risk: Bond key
Path: a byte-at-a-time comparison leaks the key length by timing, ~256 tries per
      byte against a signing oracle we run on every unlock attempt.
Mitigation: verified. mac.rs uses subtle::ConstantTimeEq::ct_eq on the whole tag
      for fixed-length arrays, with verify_is_constant_time_smoke pinning it;
      sign.rs uses verify_strict. No early return on a first-byte mismatch.
Status: mitigated (verified 2026-09-25 during this review)
```

```
ID: T-126
Title: peer_id is compared with plain equality
Severity: info
Attacker: Co-located local user
Asset at risk: none material — a peer_id is public (it is derived from the
      phone's public key and printed on screen)
Path: bond.rs documents the invariant `bond.peer_id == peer_id_from_pubkey(...)`
      using ordinary string equality. A timing difference here distinguishes
      nothing an attacker does not already see.
Mitigation: none needed. Recorded so that the next reader does not have to
      redo this reasoning, and because the skill's rule 3 makes every non-constant
      comparison worth writing down exactly once.
Status: accepted (§7)
```

```
ID: T-106 / T-107 / T-110
Title: Bond store integrity and ownership
Severity: high if violated  →  CLOSED, the modes are enforced and now guarded
Attacker: Co-located local user
Path: the store holds the bond key; a world-readable copy is the whole game.
Verification: the code enforces the modes rather than inheriting them —
      bond.rs sets 0600 on the file and 0700 on its directory, pair_recovery.rs
      sets 0600 on a temp file *before* renaming it into place (rename preserves
      the temp's mode) and 0700 on the key directory. On the reference machine
      /var/lib/syauth, keys/ and the .bin files are 700/700/600, with a umask of
      022 — which is the point: without the explicit chmod those files would be
      644, and the machine's umask would have hidden the difference.
Mitigation: `the_bond_key_and_its_directory_are_not_world_accessible` in
      pair_recovery.rs pins 0600 and 0700. It fails with "got 644" when the
      chmod before the rename is removed, which is the trap it exists for.
Status: closed (2026-09-25)
```

```
ID: T-129
Title: The bond key is a 0600 file, which D6 explicitly rejects
Severity: high
Attacker: Co-located local user; anyone who reads a backup of the home directory
Asset at risk: Bond key — the thing that authenticates every unlock
Path: /var/lib/syauth/keys/<peer_id>.bin holds the 32-byte bond key, mode 600,
      owned by the user. SPEC §3.2 D6 chooses the Linux kernel keyring
      (linux-keyutils) with libsecret as fallback, and names as a REJECTED
      alternative: "Plaintext ~/.config/syauth/; environment variable; file with
      0600 (all leak on root compromise without any defense)".
      crates/syauth-core/src/secrets.rs implements exactly what D6 asks for —
      BackendKind::Kernel, BackendKind::SecretService, an InMemoryKeyStore for
      tests, a Zeroizing payload type — and the crate root re-exports all of it.
      Nothing on the unlock path calls it. The daemon reads the file.
Likelihood: certain (it is how the product works today)
Impact: no defence in depth: the key is readable by anything that can read a
      user file, and a home-directory backup carries it
Mitigation: either wire `KeyStore` into the daemon and delete the file store, or
      change D6 and record it as a deviation. This is a D1–D8 decision, so it is
      the operator's call, not a refactor someone does on the way past.
Status: open  ·  SPEC-DEVIATION, pre-existing, surfaced 2026-09-25
```

```
ID: T-130
Title: Revoking a bond does not destroy its key material
Severity: medium
Attacker: Co-located local user, later
Asset at risk: Bond key of an association the operator believed was over
Path: revocation marks the bond `Revoked` in bonds.toml and stops the daemon when
      it was the last one, and it does not remove keys/<peer_id>.bin. On the
      reference machine 25 key files remain for 4 bonds. The operator's mental
      model after "Revoke" is that the association is gone; the key that
      authenticated it is still on disk.
Likelihood: certain
Impact: small on its own — a revoked key alone does not unlock anything, because
      the bond is not served — but it is key material whose lifetime should end
      with the association, and it accumulates silently
Mitigation: unlink the active key file in revoke_bond_by_peer_id, and sweep
      orphans on daemon start for keys with no matching bond. Both are small;
      neither touches D6.
Status: open
```

## 7. Accepted residual risks

1. **Root on the desktop reads the bond key** (SPEC T-007). Root can do anything;
   there is no defence that means anything here. Revoke on suspicion.
2. **A relay can pass the cryptographic checks.** A phone gesture is required per
   unlock (D2), which removes the passive class; the active class is bounded by
   the timing budget, which T-101 says is unmeasured. Accepting this until T-101
   closes is a decision, not an oversight.
3. **JNA ships its maintainer's build path inside `libjnidispatch.so`.** A
   third-party path in a published dependency, present in every JNA app. Not
   ours, and not fixable without vendoring and rebuilding JNA. The path is not
   repeated here on purpose: `scripts/privacy-check.sh` refuses a personal home
   directory in the tracked tree, and this document is inside the tree.
4. **The greeter PAM line is `sufficient`, not the `required` D7 describes.**
   Recorded as DEV-006 with operator approval. It preserves the password
   fallback; it is still weaker than the documented default. Listed here so it is
   not discoverable only by reading the SPEC and finding a different reality.
5. **The lock-screen adaptation is a patched DMS tree.** It is a patch against
   someone else's shell, and a DMS update can silently un-apply it. The GUI
   reports "Riavvia DMS" when the marker disagrees, which is honest; the coupling
   itself is accepted.
