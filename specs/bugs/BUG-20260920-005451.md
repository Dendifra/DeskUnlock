# BUG-20260920-005451: biometric unlock request is not reusable while phone remains present

## Summary
After the automatic DeskUnlock PAM request expires, the lock screen does not start a new DeskUnlock request during a later unlock attempt while the phone remains present.

## Reproduction
- Method: source inspection plus bridge assertions
- Evidence: `desktop/dms/build-dms-syauth.sh` invoked `dms ipc call syauth phoneReturned`, but its generated `Pam.qml` contained no `IpcHandler` for target `syauth`; the only syauth start path was the lock-secured timer. The generated bridge also had no event handler restarting syauth after a normal password PAM interaction.

## Expected Behavior
The phone-return event starts one request. If it expires, a later normal lock-screen unlock attempt can start one new request without a continuous retry loop; password PAM remains available.

## Actual Behavior
The first request could expire and leave the syauth context inactive. Presence remained true, so no later phone-return edge occurred, and the bridge did not restart syauth on a normal unlock attempt.

## Root Cause Analysis
The desktop watcher tracked the phone-return edge correctly, but the DMS bridge did not register the `syauth` IPC handler called by `syauth-proximity`. After the one-shot PAM context completed, no lock-screen interaction event started that context again.

## Fix
Register the `syauth.phoneReturned` IPC event and start syauth when the existing password PAM context becomes active during a normal unlock attempt. Both paths are guarded by the existing lock and in-progress state, so they do not create polling or retry loops.

## Traceability
- Failing evidence: `desktop/bin/syauth-proximity`, `desktop/dms/build-dms-syauth.sh`
- Fixed in: `desktop/dms/build-dms-syauth.sh`
